# Architecture

How `convoke-space/public` is put together, and why. Structural decisions that
would surprise a fresh agent belong here.

## Shape of the repository

```
site.config.ts          canonical origin, site name, navigation  (single source of truth)
next.config.ts
content/
  posts/                → /writing/<slug>
  projects/             → /projects/<slug>
  events/               → /gatherings/<slug>
src/
  app/                  App Router routes, sitemap, robots, feed, OG images
  components/           presentational building blocks
  lib/
    content.ts          filesystem content layer
    schema.ts           frontmatter validation
    seo.ts              metadata + JSON-LD builders
    site.ts             origin resolution
    format.ts           date/list formatting
    og.tsx              shared social-card layout
tests/                  vitest: schema, content, site, boundary
docs/
.github/workflows/ci.yml
```

## Rendering model

Everything is statically generated at build time. Content is read from disk with
`fs`, so there is no request-time data source, no database, and nothing to fail
at runtime. `generateStaticParams` plus `dynamicParams = false` means an unknown
slug is a 404 rather than an on-demand render.

`outputFileTracingIncludes` keeps `content/**` in the serverless output so the
site still renders correctly if a route ever becomes dynamic.

## Content layer

`src/lib/content.ts` is the only module that touches the filesystem.
`src/lib/schema.ts` is the only module that reads raw frontmatter. Pages consume
typed entries and never see a `Record<string, unknown>`.

Rules the loader enforces, all of which fail the build:

- filenames must be lowercase kebab-case (the filename is the slug)
- slugs must be unique within a collection
- frontmatter must validate, with every problem in a file reported at once
- unknown frontmatter fields are rejected
- the body must not be empty

Results are memoised per process, so a build reads each file once.

### Why a hand-written validator

A schema library would be one more dependency to keep current for the lifetime
of the site, and the requirement is small: about a dozen field types with
precise error messages. `src/lib/schema.ts` is dependency-free and covered by
`tests/schema.test.ts`. Revisit only if the schema starts growing conditional
logic.

## Design system

Tokens live in `src/app/globals.css`, defined once on `:root` and redefined
under `prefers-color-scheme: dark`. Tailwind's `@theme inline` maps them to
utility names (`bg-surface`, `text-muted`, `border-rule`), so components refer
to semantic roles and the whole palette can be retuned in one file. Components
must not introduce raw hex values.

Typography uses the operating system's own serif, sans and mono stacks. No web
fonts: nothing to download, no layout shift, nothing that can break or become
unavailable in five years. Long-form reading uses the serif stack; interface
chrome and metadata use the sans stack.

The `.prose` class is hand-written rather than supplied by a typography plugin.
The vertical rhythm of the reading surface is the product here, and it is small
enough to own outright.

## SEO and metadata

- `src/lib/seo.ts` builds all page metadata. Pages never construct their own
  Open Graph tags.
- `src/lib/site.ts` resolves the origin: an explicit `NEXT_PUBLIC_SITE_URL`
  override, else the Vercel preview URL, else the canonical origin.
  **Canonical URLs always point at production**, so a preview deployment never
  competes with the real site in search.
- Preview deployments (`VERCEL_ENV !== "production"`) serve `noindex` and a
  `Disallow: /` robots file.
- Structured data: `WebSite` on home, `Article` on posts, `Event` on gatherings,
  `BreadcrumbList` on every detail page.
- Social cards, the favicon and the Apple touch icon are all generated by
  `next/og` at build time from the same typographic layout. There are no binary
  image assets in the repository.

## Accessibility

Semantic landmarks (`header`/`nav`/`main`/`footer`), a skip link, one `h1` per
page with a descending heading order, `aria-current` on the active nav item,
visible focus rings via `:focus-visible`, `prefers-reduced-motion` honoured, and
a colour palette checked for contrast in both themes. No content is conveyed by
colour alone.

## Testing

`vitest`, four suites, no browser needed:

| Suite | What it protects |
| --- | --- |
| `schema.test.ts` | frontmatter rules and error messages |
| `content.test.ts` | the real content directory parses, ordering, draft exclusion, internal links resolve |
| `site.test.ts` | origin resolution across local, preview and production |
| `boundary.test.ts` | no private-repo dependency, no submodules, no secrets, `.env` ignored |

`boundary.test.ts` is an architecture test. When it fails, the architecture
broke — the fix is in the code, not the test.

## Deliberate constraints

- No client-side analytics, trackers, or third-party embeds.
- No runtime data source, so no availability risk beyond the CDN.
- No syntax highlighting: it would mean a large dependency for a small benefit
  today. Code blocks are styled plainly.
- No `dangerouslySetInnerHTML` except in `JsonLd`, where the payload is built
  from typed inputs and `<` is escaped.

## Extension points (not built)

The architecture leaves room for these without pre-building them: a database or
CMS behind the content layer's interface, authentication as route-group
middleware, a registration backend behind the event page's external link, and
richer MDX components through the map in `src/components/mdx.tsx`.
