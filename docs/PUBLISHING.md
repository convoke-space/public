# Publishing

How content gets onto convoke.space, and the exact schema it must satisfy.

## Where content lives

| Directory | Route | Collection name |
| --- | --- | --- |
| `content/posts/` | `/writing/<slug>` | `posts` |
| `content/projects/` | `/projects/<slug>` | `projects` |
| `content/events/` | `/gatherings/<slug>` | `events` |

The **filename is the slug**. Lowercase kebab-case, `.mdx`, no date prefix —
URLs should not have to change when a piece is revised.

## Frontmatter schema

Validated by `src/lib/schema.ts`. **Unknown fields fail the build.** To add a
field: extend the schema, document it here, extend `tests/schema.test.ts`.

### Shared by every collection

| Field | Required | Type | Notes |
| --- | --- | --- | --- |
| `title` | yes | string | ≤ 120 characters |
| `description` | yes | string | ≤ 200 characters — this is the meta description and the feed summary |
| `date` | yes | `YYYY-MM-DD` or ISO datetime | quote it, so YAML does not coerce it |
| `updated` | no | date | shown on the page when present |
| `tags` | no | string[] | lowercased and de-duplicated automatically |
| `featured` | no | boolean | reserved for future curation |
| `draft` | no | boolean | excluded from listings, routes, sitemap and feed |

`draft: true` is a staging tool, **not** a privacy mechanism. The file is still
in a public repository. Anything that must not be seen belongs in
`convoke-space/private`.

### `posts`

| Field | Required | Type | Notes |
| --- | --- | --- | --- |
| `canonical` | no | absolute URL | set when the piece was first published elsewhere |

### `projects`

| Field | Required | Type | Notes |
| --- | --- | --- | --- |
| `status` | yes | `exploring` \| `active` \| `maintained` \| `archived` | also drives listing order |
| `url` | no | absolute URL | where the project itself lives |
| `repo` | no | absolute URL | source |

### `events`

| Field | Required | Type | Notes |
| --- | --- | --- | --- |
| `end` | no | date/datetime | `date` is the start |
| `location` | yes | string | e.g. `Seoul` or `Online` |
| `format` | yes | `in-person` \| `online` \| `hybrid` | drives the structured data |
| `registrationUrl` | no | absolute URL | external only — see below |

An event is "upcoming" until its `end`, or until the close of its `date` when
there is no end.

### Example

```mdx
---
title: A title that reads as a sentence
description: One sentence that will appear in search results and in the feed.
date: "2026-09-13"
tags: ["architecture", "ai-native"]
---

Body starts here. Markdown plus MDX. GitHub-flavoured tables, footnotes and
task lists are available. Headings get anchor links automatically.
```

## Writing a new piece directly

For content that was never private working material:

1. `git switch -c content/<slug>`
2. Create the file in the right collection.
3. `npm run verify`.
4. Open a pull request. A human merges; Vercel deploys.

## Promoting from `convoke-space/private`

Material that started as private working material takes the long path:

```
private → review → edit → sanitize → promote → public → PR → CI → merge → deploy
```

**Promotion is not a copy.** It produces a clean publishable artifact. Before a
file moves, actively inspect it for:

- personal information — the author's own, and anyone else's
- credentials, tokens, internal hostnames, internal URLs
- employer, client or customer confidential material
- unpublished commercial information
- raw working notes that were never meant for a reader
- private metadata (internal ticket numbers, planning scaffolding)
- unsupported claims
- attribution problems — quotes, sources, other people's ideas

Then rewrite for a reader rather than for the author's own thinking, add
frontmatter, and open the pull request. Use the "Publication" issue template to
track it; do not paste private content into the issue.

The private repository is never a live CMS. Nothing publishes automatically.

## What happens on merge

`main` → Vercel → `https://convoke.space`. The sitemap, RSS feed and social
cards are regenerated by the build. Nothing needs to be updated by hand.

## Checklist before opening a content pull request

- [ ] Filename is lowercase kebab-case and reads well as a URL
- [ ] `description` is ≤ 200 characters and works as a search snippet
- [ ] Every internal link resolves (`npm test` checks this)
- [ ] External links use absolute `https://` URLs
- [ ] No personal information, credentials, or third-party confidential material
- [ ] Claims are supported and sources are attributed
- [ ] `npm run verify` passes
