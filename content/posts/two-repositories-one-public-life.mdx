Most personal sites have one repository. Content and code sit together, the
half-finished essay lives in a folder called `drafts/`, and the only thing
standing between a raw note and the open internet is a filter in a listing
function. It works right up until the day it doesn't.

Convoke is built on two repositories instead. `convoke-space/public` holds the
application and everything published. `convoke-space/private` holds drafts,
research, raw notes, and material that may never be published at all. The
production site is built from the public repository alone.

That last sentence is the load-bearing one, so it is worth being precise about
what it rules out.

## What the boundary forbids

A tempting design is to keep one repository public, one private, and have the
build pull content across at deploy time — a token in the environment, a clone
step in the build, a merge of the two content trees. It gives you the privacy
story and the single-source-of-truth story at once.

It is also a trap. That design means:

- production cannot be rebuilt from what you can see;
- a leaked build token exposes every unpublished draft;
- a broken credential takes the site down;
- the private repository has quietly become a CMS with no review step.

So Convoke forbids it outright. No submodules across the boundary, no build-time
clone, no runtime fetch. A clean machine with access to nothing but the public
repository must be able to run `npm ci && npm run build` and produce the site.
If that stops being true, something has gone wrong architecturally, not just
operationally.

## Publication as an event

Once the build cannot reach across, publishing has to become a deliberate act.
Material moves in one direction and one direction only:

```text
private → review → edit → sanitize → promote → public → PR → CI → merge → deploy
```

The interesting word there is **sanitize**. Promotion is not a copy. A draft
carries things a published piece should not: a client's name used as shorthand,
a number someone shared in confidence, a paragraph written to think out loud
rather than to be read, an assertion that felt true at 1am. The promotion step
exists so that someone — a human, or an agent following a written checklist —
has to look at the file with publication in mind before it moves.

Filtering drafts with a `draft: true` flag never forces that pause. A repository
boundary does. The friction is the feature.

## The second-order benefit

The privacy argument is the obvious one, and it is real. But the boundary turns
out to buy something less obvious: it makes the private repository *safe to be
messy*.

When everything lives in one repository, every note is written with a small
amount of self-consciousness, because it is one careless commit away from being
public. Separating the two removes that. Research can be unstructured. Notes can
contradict each other. A draft can be wrong on purpose while an idea is being
worked out. Nothing there is pretending to be finished.

That is the actual point of a private workspace, and you only get it if the
boundary is credible enough that you stop thinking about it.

## Making it hold

Boundaries decay unless something maintains them. Three things maintain this
one:

1. **An architectural invariant, written down.** The public repository's
   `AGENTS.md` states that production must build from the public repository
   alone. Any future change that violates it is not a judgement call.
2. **A promotion checklist.** The private repository's `AGENTS.md` describes
   what to inspect before moving a file: personal information, credentials,
   third-party confidences, unsupported claims, attribution.
3. **CI that builds from a clean checkout.** Every pull request installs
   dependencies and builds the site with nothing but the public repository
   available. If a private dependency ever sneaks in, the build stops being
   reproducible and the pipeline says so.

None of that is elaborate. It is roughly one paragraph of documentation, one
checklist, and one workflow file. The cost of maintaining the boundary is
supposed to be near zero — otherwise it is the kind of discipline that survives
three months and then quietly stops.

## What it does not solve

Git history is forever. If a credential or a private detail is ever committed to
the public repository, deleting the file does not remove it — the object is
still reachable, and it has probably already been cloned and indexed. The
boundary reduces how often that can happen; it does not make it recoverable.
Anything exposed is treated as compromised and rotated, not tidied away.

That asymmetry is the whole reason to put the wall up before there is anything
worth protecting behind it.
